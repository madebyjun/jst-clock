# 機械で読める時刻コードの設計

設定の「機械可読タイムコード」で表示する（保存される）。`?code=1` / `?code=0` はその表示の間だけの上書きで、保存しない（`?tz` `?lag` と同じ扱い）。

画面をカメラで撮影した映像から、1フレームごとに「その画面が何時を表示していたか」と「どんな補正をかけていたか」を機械的に読み取れるようにする。実装より先に書いた。

## 前提：何を読み取れれば十分か

- **画面の時間分解能はリフレッシュ周期で決まる。** 60Hzの画面は1枚の絵を16.7ms出し続ける。どれだけ細かく時刻を符号化しても、撮影された1枚から分かるのは「どの表示フレームが（どの割合で）写ったか」まで。ms単位の値は「その表示フレームが何時として描かれたか」を正確に伝えるために使う。
- **符号化する値は「表示値」であって、露光時刻ではない。** 表示フレームの時刻は、数字と同じ「次に表示される時刻の予測値」。`clock.now(performance.timeOrigin + rafTs + frameMs + lag)` の値を `Math.floor` したms（数字の表示と同じ値）を符号化する。数字と同じ rAF の中で、同じ値を使って描く。この予測は rAF の時刻にフレーム間隔を足しただけで、合成・パネルの応答・スキャンアウトによる実際の提示の遅れは含まない（`?lag` で手で足す）。撮影した瞬間の正しい時刻を求めるには、別に露光時間・実際の切り替わり時刻・ローリングシャッターの読み出し時間の較正が要る。デコーダはそれを推定せず、表示値と混ざった割合だけを返す。
- **撮影側で起きること**（どれもカメラ側では避けられない前提として扱う）
  - 露光が表示の切り替わりをまたぐと、2枚（シャッターが遅ければ3枚）の表示フレームが**加重平均で混ざる**。59.94p で 60Hz の画面を撮ると、混ざる位相が約17秒周期でゆっくり一巡する。30p・1/30秒では毎フレーム必ず混ざる。
  - ローリングシャッター（α7 III やスマホ）は行ごとに露光時刻が違うので、表示の切り替わりが**水平な境目で上下に分かれて**写る。画面自身も上から順に書き換わる（スキャンアウト）。
  - 露光オーバーで白が膨らむ（ブルーミング）、モアレ、圧縮ノイズ、ガンマ（混ざり方は線形光で起き、映像は非線形で記録される）、OLED の PWM 調光による明暗の縞。

## 選択肢の評価

### A. QRコードを毎フレーム切り替える

依頼にあった案。結論として**毎フレームの時刻には向かない**。

- 混ざったフレームは2つのQRの重ね書きになり、ほぼ確実にデコードに失敗する。59.94p/60Hz の組み合わせでは、混ざる位相の区間がまとまって続くので、読めない区間が数秒単位で続く。30p・1/30秒では全滅しうる。
- ローリングシャッターで上下が別のQRになると、ファインダーパターンは見つかるのに誤り訂正で直せず失敗する（最悪、Reed-Solomon が片方に「訂正」してしまう。これは誤りではないが、どちらに寄ったか分からない）。
- 同じ面積なら、QRのモジュールは専用の符号のセルより何倍も小さい。v5（37モジュール）を画面幅の20%に描くと、1920px幅の映像に画面全体が写っていても1モジュール10px程度で、少し引くとピンぼけと圧縮で崩れる。
- 混ざった割合（＝露光の中心が表示の切り替わりからどれだけずれていたか）という、サブフレームの情報を一切取り出せない。
- 描画コスト自体（lean-qr の生成は1ms未満）は問題ではない。問題は読み取り側。

ただし**ゆっくり（1〜2Hz）切り替えるQRは有用**。切り替わりのフレーム以外はきれいに写るので確実に読め、一般のQRリーダーでも読める。補正の詳細のように桁数は多いが毎フレーム変わる必要のない情報に向く。

### B. 1次元バーコード（Code128 など）

- 縦縞なので、1本の走査線に沿って読めばローリングシャッターの上下分割の影響は受けにくい。
- しかし混ざりには弱い（細いバーとスペースの幅で符号化するので、重ね書きで幅が崩れる）。モジュール幅が細く（Code128 は1文字11モジュール）、距離に弱い。混ざりやサブフレーム情報への手当てがない点はQRと同じ。

### C. 専用の時間符号（帯状の大きなセル）

計測用の LED タイミングボードやカメラ同期用スレートと同じ発想で、時刻を読むためだけの帯を描く。設計の自由度を次の問題に使える。

- **グレイコードのフレーム番号**：連続する値で1ビットしか変わらないので、2枚が混ざったフレームでも「変わったビットだけが中間の明るさ」になり、どちらかの値か、その2つの間だと分かる。第3の値にはならない。さらにその1ビットの明るさの割合が、露光の中心が切り替わりのどちら寄りだったか（**バーニヤ**）を表す。
- **差動（マンチェスター）セル**：1ビットを「白黒」「黒白」の2セルの組で描き、左右どちらが明るいかで読む。混ざったフレームでは、すべての変化ビットで「多く写った方の値」が読まれる（左右の明るさの大小は、ガンマや露出がどうであれ混ざった割合の大小と一致する）。しきい値を使わないので、ガンマ・露出・照明むら・ブルーミングに強く、どちらの値かを全ビットで一貫して選べる。左右の差が小さい組は「判定不能」として扱える。
- **横長の行に並べる**：1つの行のセルは映像上の同じ行にあるので、ローリングシャッターでもほぼ同時刻に露光される。行と行の境で上下に分かれた場合は、行をまたぐチェック（CRC）で検出する。
- **大きなセル**：36×6 モジュール程度なら、スマホ幅でも1セル10 CSS px 以上、デスクトップでは20px以上にできる。
- 限界：一般のリーダーでは読めない。専用のデコーダが要る。

### D. その他

- **アナログ表示（流れるバーや光点）**：画面は1表示フレームに1状態しか出せないので、ms単位で動く光点を描いても、1枚から分かるのはやはり表示フレーム単位。明るさで位相を表す方式はガンマ・露出に弱い。
- **音声タイムコード（LTC）**：カメラの同期では標準的な方法だが、端末の音声出力の遅延（Bluetoothでは数十〜数百ms）が不明で、画面の時刻とは別物になる。対象外。

## 採用する設計：グレイコードの時刻帯 ＋ ゆっくり切り替わるQR

### 時刻帯（毎フレーム）

```
 ┌──────────────── 白枠（1モジュール） ────────────────┐
 │ W B │ b15 b14 … b0（16ビット×2セル） │   行0: グレイコード(n mod 2^16)
 │ W B │ t[27..12]                        │   行1: 時刻の上位
 │ W B │ t[11..0] flags(4)                │   行2: 時刻の下位 + フラグ
 │ W B │ CRC-16                           │   行3: 行0〜2のCRC
 └──────────────────────────────────────────────────┘
 周囲に黒の静寂域（2モジュール以上）
```

- 格子は 36列 × 6行のモジュール（白枠1 + 34セル + 白枠1、白枠1 + 4行 + 白枠1）。外側に黒の静寂域。
- 各行の先頭2セルは白・黒の基準。行ごとのコントラスト（PWMの縞や露出のむらで行ごとに違う）をここで測る。
- 残り32セルが16ビット。ビット1は「白黒」、ビット0は「黒白」。上位ビットから。
- 行0：描いたフレームの通し番号 n（描画ごとに1増える）の下位16ビットのグレイコード。60Hzで約18分で一巡するが、デコーダは連続性とQRの通し番号で巻き戻しを解く。
- 行1・2：時刻 t（Unix ms、`Math.floor`）の下位28ビット（約74.6時間で一巡。上位はQRの完全な時刻か、利用者が与える基準時刻で補う）。
- フラグ4ビット：同期済み（`clock.now` が値を返した）、照合済み（画面の緑の点と同じ条件：過半数一致・2つ以上・ホールドオーバーでない）、寄せ中（表示している時刻が同期の推定値から誤差上限より離れていて、なめらかに寄せている途中。E2 の処理のため）、形式の版（1ビット、現在0）。未同期なら t は0で同期済みフラグが0（端末の時計を正しい時刻のように見せない、S3と同じ方針）。
- 行3：行0〜2の48ビット（6バイト）に対する CRC-16/CCITT-FALSE（多項式 0x1021、初期値 0xFFFF）。CRC はフレーム番号も含むので、時刻が読めたフレームでは番号も検証済みになる。

画素の描き方：

- 1モジュールを**整数のデバイスピクセル**にし、キャンバスのビットマップを CSS サイズ × devicePixelRatio に一致させ、`image-rendering: pixelated` で拡大縮小の補間を避ける。アンチエイリアスなしの塗りつぶしだけで描く。
- 白は `#fff`、黒は背景と同じ近黒色。

### メタデータQR（2Hz）

- 500ms ごと（表示する時刻 t の 500ms の区切りをまたいだフレーム）に作り直す。中身はその瞬間のフレームの値で、次に作り直すまで同じ絵を出し続ける。
- 標準の極性（白地に黒、静寂域4モジュール）・誤り訂正 M。スマホのQRリーダーでもそのまま読める。英数字モードに収まるよう、大文字・数字・記号だけで書く。
- 形式（空白区切り、先頭が版）：

```
JC1 N<n> T<t> F<frameMs> L<lag> D<端末時計−正しい時刻 ms> U<±ms> E<表示−推定 ms> R<端末の時計の速さ ppm> Q<±ppm> A<一致数> S<応答数> H<0|1> K<同期の回数> Z<分> V<版>
例: JC1 N4521 T1760000000123 F16.667 L0 D-12.3 U4.5 E0.0 R-3.2 Q1.1 A4 S5 H0 K12 Z540 V1A2B3C4
```

  - N, T：このQRを描いたフレームの通し番号（巻き戻しなし）と時刻（ms）。時刻帯の巻き戻しを解く基準。中身は N のフレームでのスナップショットで、次のQRの N の手前まで有効（補正がその間に変わることはある。フレームごとに変わりうる「寄せ中」だけは時刻帯のフラグで毎フレーム伝える）。
  - F, L：描画補正（次のフレームの表示時刻を予測するために足しているフレーム間隔と、`?lag` の手動分）。
  - D, U, E：端末の時計のずれ（表示している時刻に対して）、表示している時刻そのものの誤差上限（画面の ± と同じ `clock.shownError()`。E2 のなめらかな寄せで推定の中心から離れている分を含む）、表示している時刻と同期の推定の中心との差。R, Q：学習した端末の時計の速さ（未学習なら `R-` `Q-`）。A, S, H, K：一致した時刻源の数・応答した数・ホールドオーバー中か・それまでの同期の回数（補正の状態が変わったかの目印）。
  - Z：設定で選んだタイムゾーンの、その時刻での UTC からのずれ（分、JST は540）。ゾーン名は英数字モードに収まらない（小文字や `_`）ので載せない。時刻帯とQRの T は常に UTC の Unix ms。V：アプリの版（ビルド時の git コミット）。
  - 未同期のときは `T-` とし、D, U, R, Q も `-`。

### 配置

- 時刻の数字（`#time`）と進捗バーの下、状態表示の上に置く。数字には重ねない。
- 横幅が広いときは時刻帯（幅の約70%）とQR（約20%）を横に並べ、狭いとき（スマホ）は時刻帯を全幅、その下にQRを置く。横にはみ出さない。
- 数字と縦方向に近い位置に置く理由：液晶は上から順に書き換わる（スキャンアウトに最大1フレーム）。数字と符号が近いほど、両者の表示時刻の差が小さい。

### デコード

`tools/decode-timecode.ts`（node、ffmpeg で映像・画像を8ビットのグレースケールに展開）。

1. **位置の特定**：明るい画素の連結成分のうち、外接矩形の縦横比が白枠（36:6）に近く、内側に暗い画素を含む（中が詰まった白い矩形である進捗バーと区別する）ものを探す。成分の四隅（x+y の最小・最大、x−y の最小・最大）から射影変換を求めるので、多少の傾き・台形は許す。見つけた位置は次のフレームでも使い、読めなくなったら探し直す。手で `--corners` を与えることもできる（三脚撮影で白枠が他と繋がってしまう場合）。
2. **セルの読み取り**：各セルの中央40%の範囲を平均する（縁のにじみやブルーミングを避ける）。行ごとに基準セルの白と黒の差をコントラスト C とし、差動の組について d = (左 − 右) / C を求める。d > 0 なら1。|d| < 0.25 は判定不能。C が小さすぎる（白枠が写っていない・露出が極端）ときは `lowcontrast`。
3. **混ざり方の判定（行0）**：|d| < 0.6 の組を「混ざったビット」とする。混ざっていないビットは基準セルと同じ全振幅（|d| ≈ 1）になるはずなので、混ざったビットの数がそのまま「変化したビットの数」になる。グレイコードでは連続する2フレームの混ざりは必ず1ビット、3フレーム以上なら2ビット以上。
   - 0個：1枚だけ写っている。
   - 1個：その1ビットを0/1にした2つの値が連続する（差が1）ときだけ「n と n+1 の2枚の混ざり」とし、混ざった割合を d から求める（`frac`、後の値の重み。線形光の仮定なので近似で、露光時刻ではない）。連続しなければ `multi`。
   - 2個以上：3枚以上の混ざり（露光が表示周期より長い）か誤読。`multi` として何も返さない。この場合、各ビットの多数決が3枚のどれとも違う値になりうる（例：127→144→160 が等量で混ざると多数決は176）ため、時刻も読まない。
4. **時刻（行1〜3）**：行0が0個か1個のときだけ読む。判定不能（|d| < 0.25）が1つでもあれば時刻は読まない（`blend`）。全ビット読めて、行0の番号（1個のときは2候補のどちらか）と合わせて CRC が合えば確定。混ざっていなければ `ok`、2枚の混ざりなら `mixed`（多く写った方の値。差動セルなので全ビットがそちらにそろう）。CRC が合わなければ `torn`（行の間で上下に分かれた・誤読）。
5. **時刻の補完（`t_est`）**：フレーム番号は描画ごとに1増えるだけで時間軸ではない（描画が止まれば、番号は1しか進まないのに時刻は跳ぶ）。グレイコードの行には冗長性がなく、確信を持って誤読したビットは検出できない。そこで、確定していないフレームの時刻は、前後8フレーム以内の確定フレームに挟まれ、番号がその間にあり、挟む2つの確定フレームの「時刻の差 / 番号の差」が映像全体の典型値から±25%以内（間に描画の停止がない）ときだけ線形補間して `t_est` に出す。`t_ms` とは別の列で、確定値としては扱わない。QR の N, T, F からの外挿はしない。
6. **巻き戻しの解消**：n は前のフレームからの差が最小になるよう、t はQRの完全な時刻（なければ `--around`）にいちばん近くなるよう、上位を補う。

出力はフレームごとの CSV：`frame, pts, status, n, n_hi, frac, t_ms, t_iso, t_est_ms, synced, verified, slewing, qr`。`status` は `ok`・`mixed`（時刻を確定）、`blend`（2枚の混ざりで n〜n+1 だけ分かる）、`torn`、`multi`（3枚以上の混ざりか矛盾）、`unsynced`、`lowcontrast`、`nocode`（位置が分からない）。

#### 混ざったフレームで「第3の値」にならない根拠と、その適用範囲

前提は「露光が表示周期以下で、写るのは連続する2枚まで」「帯がほぼ水平で、1つの行が映像上ほぼ同じ高さ（同じ露光時刻）に写る」こと。帯が傾くとローリングシャッターでは行の左右で露光時刻が違い、セルごとに混ざる割合が変わるので、この根拠は成り立たない（その場合は `multi`・`torn`・CRC で棄却されることを期待するだけになる）。

- 差動セルは、2枚 A, B の混ざり（重み w, 1−w）で、ビットが異なる組の左右の明るさが f(w) と f(1−w)（f は単調なカメラの応答）になる。大小は w と 1−w の大小だけで決まるので、すべての変化ビットが同じ側（多く写った方）に読まれる。w ≈ 0.5 では差が小さく判定不能になる。したがって、セル単位の雑音が判定不能の幅を超えない限り、読めた値は A か B のどちらか。
- それでも残る誤読（ノイズ・ブルーミング・圧縮）は CRC-16 で検出する（偶然一致は約 1/65536）。
- グレイコードの行は、連続する2値では1ビットしか変わらないので、混ざったビットが1個のときの2候補が連続していることを確かめれば、無関係な値を候補にしない。3枚以上の混ざりは、混ざったビットが2個以上になることで検出する。ただし3枚目の重みが小さい（約2割未満）と全振幅との差が埋もれて2枚と見分けられないので、その場合の保証は判定不能の幅と CRC に頼る。

## 撮影のおすすめ

- 三脚で正対し、時刻帯の1モジュールが映像上で8px以上になるように撮る（QRも読ませるなら1モジュール4px以上）。
- シャッター速度は表示周期より十分短く（60Hzの画面なら 1/250〜1/500）すると混ざるフレームが減る。ただし OLED の PWM 調光と干渉して暗いフレームが出るときは遅くする。表示周期より長い露光（60Hzに 1/30 など）では毎フレーム3枚が混ざり、ほとんど `multi` になる。
- 帯が水平に写るように構える（傾きは上の前提を崩す）。
- 露出は白枠が飽和しすぎない程度に。白が膨らむとセルの境界がにじむ（中央だけ読むのである程度は耐える）。
- ローリングシャッターでは、映像の行ごとに露光時刻が違う。読み取った値は「時刻帯が写っている行で、どの表示値が見えていたか」なので、ほかの被写体と比べるときは読み出し時間 ×（行の差 / 画面の高さ）を補正する。

## 確認（E2E）

- 決まった時刻を描かせたスクリーンショットから、デコーダがその時刻をそのまま返す。
- 連続する2フレームを合成した画像（混ぜる割合を変える、sRGB で混ぜる・線形光で混ぜる、上下に分割する）と、連続する3フレームを合成した画像から、写したどれかを返すか無効とし、写していない値を返さない。誤った確定値の数と読み取り率を記録する。
- 実際のページを Playwright の録画で撮り、デコードした時刻が単調・連続で、ページが実際に描いた (n, t) と一致する。
- `?code=1` がなければ何も描かない。数字と重ならず、スマホ幅で横にはみ出さない。

デコードした CSV とスクリーンショットは `artifacts/timecode/` に残す。

## 実機で確かめていないこと

E2E はスクリーンショットと Playwright の録画（ブラウザが合成した絵をそのまま取り込む）なので、パネルの応答・スキャンアウト・カメラの露光・ローリングシャッター・PWM・レンズのぼけは通らない。実機では次を撮って、元の動画・撮影設定・CSV・再実行コマンドを残し、誤った確定値の数（隣り合う確定値の差が映像の時間差と食い違う数）と読み取り率を数える。

- α7 III 59.94p で60Hzの画面を、混ざる位相が一巡する20秒以上。シャッター 1/60・1/250・1/1000。
- 表示周期より長い露光（30p・1/30）。`multi` になり、確定値を返さないこと。
- 帯を数度傾けた撮影。
- スマホ（OLED、PWM 調光）を 30/60/120fps で。

## レビューで変えたこと（Codex）

最初の案に対する Codex のレビューを受けて、次を変えた。

1. **フレーム番号を時間軸として外挿しない。** 番号は描画ごとに1増えるだけなので、描画が止まると番号と時刻の比例が崩れる。QR の `T + (n − N) × F` による推定をやめ、前後の確定フレームに挟まれ、間に停止がないと確かめられるときだけ補間する（`t_est`、確定値とは別列）。
2. **「第3の値にならない」の前提を明記し、3枚以上の混ざりを検出する。** 露光が長いと3枚が混ざり、各ビットの多数決がどれとも違う値になる（127→144→160 → 176）。全振幅に届かない「混ざったビット」を数えて、グレイコードの行で2個以上なら `multi` として何も返さない。帯の傾きも前提を崩すことを書いた。E2E に3枚の合成を加えた。
3. **グレイコードの番号は無保護であることを踏まえる。** CRC がフレーム番号も覆うようにし、確定値の番号は検証済みにした。確定していない番号は補間の条件（前後の確定値に挟まれる）でしか使わない。
4. **表示値と露光時刻を区別する。** `t_ms` は表示値、`frac` は混ざった割合で、露光時刻への変換は露光時間・実際の切り替わり時刻の較正が要ると書いた。
5. **フレームごとの補正の状態を伝える。** QR は500msごとのスナップショットなので、表示値が同期の推定から離れて寄せている途中か（E2）を時刻帯のフラグで毎フレーム伝え、QR に表示と推定の差 `E` と同期の回数 `K` を足した。
6. **E2E で通らない経路を明記する。** 実カメラでの確認項目を「実機で確かめていないこと」に挙げた。

採らなかった提案：表示側で (セッションID, n, t, 補正値) を保存し、映像には短いIDだけを描く方式。読み取りの負担は減るが、映像の外にログを持ち出す運用が要り、ログを失うと映像から何も分からなくなる。映像だけで完結することを優先した（ページ内の描画ログは E2E の照合用に `window.__timecode` で見られるようにする）。
